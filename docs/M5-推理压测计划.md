# M5 推理压测计划（vLLM vs SGLang）

> 状态：计划已定，待 M4 模型产物（SFT/DPO adapter）就绪后执行
> 目标（PRD M5）：推理性能压测、部署形态与成本核算、故障演练的前置数据

## 1. 为什么压测必须在"可服务化"的模型上做

M4 产出的是 **QLoRA adapter**（训练形态），M5 要评估的是**推理形态**：

- vLLM / SGLang 都不支持直接加载 4-bit QLoRA adapter；
- 服务化路径可选：
  | 路径 | 做法 | 适用 |
  |---|---|---|
  | A. 合并后 4-bit 量化（AWQ/GPTQ） | merge adapter → 量化 → vLLM 加载 | 生产推荐 |
  | B. 合并后 fp16/bf16 | merge 后直接 vLLM | 精度对照/小模型验证 |
  | C. llama.cpp GGUF | 量化 + CPU/GPU 混合 | 边缘/降级路径 |

M5 先在**本地 8GB** 用 B 路径跑通 vLLM + SGLang 的最小链路（0.5B/1.5B 或 3B+小 KV cache），
再在**云 GPU** 上跑正式压测（3B/7B），两套数据分列，不混报。

## 2. 本地链路验证（RTX 4060 8GB）

| 项 | 计划 |
|---|---|
| 引擎 | vLLM（WSL2 CUDA 12.4，独立 venv，避免污染训练环境）；SGLang 同环境 |
| 模型 | Qwen2.5-0.5B-Instruct / 1.5B（fp16）先行；3B 视显存（KV cache 需 ≤2GB） |
| 压测工具 | 自研固定并发脚本（见下）+ `vllm bench serve`（如可用） |
| 指标 | TTFT、TPOT/ITL、吞吐（req/s、output tok/s）、P50/P95/P99 延迟、显存峰值 |
| 并发档位 | 1 / 4 / 8 / 16（本地 8GB 预计 8 并发即 OOM，记录边界） |
| 输出 | `docs/M5-本地链路压测.md`（如实标注"链路验证，不代表生产容量"） |

## 3. 云上正式压测（M5 主体）

| 项 | 计划 |
|---|---|
| GPU | 阿里云 gn7i（A10 24GB）按量，与训练共用/复用；备选 AutoDL 4090 24GB |
| 模型 | M4 产出（3B SFT/DPO）merge+AWQ；对照 Qwen2.5-7B-Instruct |
| 引擎 | vLLM（PagedAttention、continuous batching） vs SGLang（RadixAttention） |
| 并发 | 1 / 8 / 32 / 64；输入 ~600 tok（规则目录+素材），输出 ≤256 tok |
| 指标 | 吞吐、TTFT/TPOT 分位、P99、显存峰值、启动时间、成本（元/千次判定） |
| 对照 | 与 M3 规则判定（~50–150ms/次 CPU）对比：什么场景值得上模型 |
| 输出 | `docs/M5-推理压测报告.md`：引擎对比表、容量结论、单位成本、选型建议（ADR-0006） |

## 4. 压测脚本设计（避免自嗨）

1. 固定输入集：M4 eval 集抽样 200 条（与训练无关的 held-out）；
2. 客户端并发由 1 递增，每档预热 20 请求后统计 100 请求；
3. 记录服务端指标（vLLM `/metrics`：queue time、KV cache usage）与客户端指标；
4. 每档重复 3 次取中位数，报告 P50/P95/P99；
5. 失败/超时按错误率单列，不混入成功延迟；
6. 成本按云实例时价 ÷ 实测 QPS 折算"元/千次判定"。

## 5. 故障演练（M6 前置，M5 收尾时做一次）

| 演练 | 预期 |
|---|---|
| 推理服务 kill -9 | 网关降级 manual（已有 M3 降级逻辑），上传链路不失败 |
| 引擎 OOM（高并发） | 请求超时 → 降级，不雪崩；记录恢复时间 |
| adapter/模型文件缺失 | 启动失败但 readiness 不通过，流量不进入 |

## 6. 选型倾向（待数据验证）

- 若 SGLang 在 RadixAttention（共享 system prompt 前缀）下 TTFT 明显更低 → 首选 SGLang；
- 若 vLLM 生态/量化支持（AWQ 4bit）更成熟、吞吐相当 → 首选 vLLM；
- 结论必须由 M5 实测数据支撑，写入 ADR-0006，不能只凭社区口碑。
