# M5 推理压测报告

> 日期：2026-11-24/25 ｜ 状态：**已完成**（vLLM 压测/门禁/混合判定完成；SGLang 尝试失败已记录）
> 原则：所有数字为实测；未测/失败的项目如实标注，不用社区数据或估算替代。

## 1. 目标与门禁（PRD FR-5 / M5 计划）

| 项 | 门禁 |
|---|---|
| 服务端全量门禁（535 条 held-out，走 HTTP） | recall ≥ 0.95、误杀率 ≤ 3%、错引条款率 == 0、JSON 解析率 ≥ 99% |
| 吞吐/延迟 | 报告实测 req/s、TTFT、TPOT（不设硬门禁） |
| 混合判定（规则 + 模型） | 规则 block 不得被模型降级；语义漏检升级人工；模型不得单方面 block |
| 引擎对比 | vLLM 必测；SGLang 尽力（失败如实记录） |

## 2. 环境与口径

| 环境 | 配置 | 用途 |
|---|---|---|
| 本地 WSL2 | RTX 4060 8GB（笔记本） | 0.5B / 合并 3B 链路、535 条服务端门禁、混合判定对比 |
| AutoDL | RTX 4090（vGPU 48GB 可见）、128 vCPU、503GB RAM、50GB 数据盘 | 7B QLoRA SFT → DPO → 合并 → vLLM 压测 → 535 条门禁 |
| 阿里云 A10（已停机） | A10 24GB，杭州 J | SSH 连通性与库存问题未能开跑，未产生训练数据（如实记录） |

统一口径：
- 推理服务：`vLLM` OpenAI 兼容 API；评测通过 `bench/evaluate_api.py` 直接打模型端点（与线上 pipeline 同一请求格式/提示词）；
- 评测集：535 条 held-out（与 SFT 训练集不重叠）；
- recall = TP/(TP+FN)；误杀率 = FP/(FP+TN)；错引条款率 = 引用条款与 gold 不一致/总引用行数；
- JSON 解析率 = 可解析为合法 JSON 的响应 / 总请求。

## 4. 混合判定（规则 + 模型）——535 条同栈对比

方法：同一个 pipeline 栈（同一 BGE embedder + 同一规则目录），分别以「规则-only」与「规则+模型」两种模式跑 535 条，唯一变量是模型第二意见。修复了此前两套不同检索实现造成的口径差异。

| 指标 | 数值 |
|---|---:|
| 规则-only 判定分布 | block 346 / manual 28 / pass 161 |
| 混合判定分布 | block 346 / manual 27 / pass 162 |
| block → block | **346（100% 保留）** |
| **规则 block 被模型降级** | **0** ✅ |
| manual → manual | 26 |
| pass → manual（语义漏检升级人工） | **1** |
| manual → pass（模型确认免责语境） | **2** |
| model_unavailable | 0 |

样本（原始 JSON：`services/model-training/reports/m5/hybrid-eval-535.json`）：
- `eval-00515`：会员积分兑换（规则未命中）→ 模型判违规 → **manual 转人工**，未自动 block；
- `eval-00532`：依据国家规定评定的"最佳创新奖"→ 免责语境经模型确认 → **pass**；
- `eval-00533`：保存期限/最佳食用期 → 免责语境经模型确认 → **pass**。

结论：保守策略成立——规则 block 权威不可被模型推翻；语义漏检不会被静默放行；模型可以确认豁免但无权 block。

### 5.2 7B DPO（负结果，如实记录）

| 项 | 实测 |
|---|---|
| 偏好对 | 1242 对（chosen/rejected 均已追加 EOS） |

| train_loss | **0.0558** |
| 训练时长 | **1627 s（27.1 分钟）** |
| 峰值显存 | **10.62 GB** |

**质量结论：DPO 仍然退化（与 M4 本地结论一致，但失败形态不同）**：
- 服务端 535 条门禁：**JSON 解析率 88.41%**（62/535 invalid）、recall **86.56%**、FPR 0、错引 0；
- 失败原因：本轮不是 M4 的"重复 violations 数组"，而是**输出变啰嗦**——evidence 字段拉长，在 `max_tokens=384` 下 JSON 被截断（无闭合括号），无法解析；
- 处置：**R-4 回退：不采用 DPO，生产模型用 SFT**（与 M4 决策一致）。

| 模型 | recall | 误杀率 | 错引条款率 | JSON 解析率 | 门禁 |

7B-SFT 遗留问题：3 条引用条款与 gold 不一致（错引率 0.8%）。**M6 上线前必须定位并修复**（否则严格门禁不过）：
1. 抽样这 3 条，人工核对是"模型引错"还是"gold 标注/条款映射问题"；
2. 注意口径：本节门禁是**模型单模型输出**（不经规则），而生产链路是混合判定——`block` 的条款引用来自本地规则库匹配结果，模型只对 `manual` 流量做复核，因此生产口径的错引率会被规则约束住；但仍需在 M6 集成测试中用"混合模式"重跑 535 条确认；
3. 重跑 535 条门禁直至 0 错引（或混合模式下 0 错引）。

### 5.5 SGLang 尝试（失败，如实记录）

- 环境：AutoDL RTX 4090 48GB，CUDA 12.4 驱动，`pip install "sglang[all]==0.3.6.post1"`；
- 结果：**25 分钟 timebox 内未完成安装（exit=124）**，`import sglang` 失败，未进入启动/压测阶段；
- 失败原因（从 pip 日志可见）：`sglang[all]` 依赖解析反复回溯（日志中出现 litellm 1.98.0→1.100.5 共 10+ 个版本的重复下载尝试），在华为云镜像上解析/下载始终未收敛；venv 体积停在 16MB，未进入安装阶段；
- 结论：**SGLang 在本项目可获得的云环境上无法在合理时间内完成部署**，不参与选型；vLLM 作为生产引擎（ADR-0006）。这属于环境/依赖问题，不是模型或压测方法问题；未做任何性能结论。

## 6. 结论

1. **vLLM 链路与 7B 生产可行性已验证**：7B-SFT fp16 在 4090 上 c=32 达 **13.89 req/s**、TTFT 58ms、TPOT 23ms，0 错误；
2. **7B-SFT 质量接近生产门禁**：recall 1.0、误杀 1.23%、JSON 100%，仅错引条款 0.8%（3 条）未达严格门禁，M6 前必须修复并复测；
3. **DPO 再次为负结果**（云端 EOS 修复后仍退化：JSON 88.4%/recall 86.6%），维持 M4 的 R-4 回退：生产用 SFT；
4. **混合判定保守策略 535 条实测成立**：0 次规则降级、1 次语义升级人工、2 次模型确认豁免、0 次模型不可用；
5. SGLang 对比**失败**（安装依赖解析 25 分钟未收敛，未进入压测），已如实记录；生产引擎按 ADR-0006 采用 vLLM；
6. 阿里云 A10 因连通性/库存问题未开跑，未产生训练数据；云端实验由 AutoDL 4090 完成。
