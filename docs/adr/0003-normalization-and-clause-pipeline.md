# ADR-0003：归一化流水线与条款解析的实现位置

- 状态：已接受（M2）
- 日期：2026-11-22
- 关联：PRD FR-3 / FR-4 / ADR-1 / ADR-2；P2-技术设计 §3.2、§4.1、§5

## 背景

M2 要解决两件事：

1. **变形对抗**（FR-3）：关键词库追不上拼音/拆字/谐音/emoji/零宽/繁简/同义替换，
   而且"追不上"必须能被量化（命中率 ≥0.95），否则无法证明改进；
2. **法规结构化**（FR-4 前置）：法规文本要变成「条文-词族-判定条件-罚则」，
   新规上线只改数据不改代码（ADR-1）。

## 决策

### 1. 归一化放在 Python 服务，而不是 Go 网关

- Go 侧只做 I/O 与编排；文本语义在 Python（`services/pipeline-py`）。
- 理由：`pypinyin` / `opencc` / 后续 embedding、模型推理生态都在 Python；
  Go 侧做 CJK 归一化要自己造轮子，且 M4 训推链路本来就在 Python。
- 代价：多一跳网络（本机 <5ms）；网关需要可降级（归一化服务不可用时退化为原文匹配 + 告警）。

### 2. 归一化输出必须带原文 offset 映射

每个归一化字符记录它来自原文的 `[start, end)` 区间（拆字 2→1 合并区间），
因此命中结果可以回指原文 span（FR-8 条款级定位），而不是只能返回"命中/未命中"。

### 3. 拼音不做"文本还原"，做"模式侧展开"

- 不把 `zui hao` 改写成汉字：拼音多对一，改写必然丢信息、破坏 offset；
- 反向生成：从词典词条生成拼音形态（无声调 `zuihao` / 带声调数字 `zui4hao3`），
  在**compact 文本**（仅 ASCII 字母数字）上匹配，再把 compact span 映射回原文。

### 4. AC 自动机自研（纯 Python）

- 模式规模 ~10³，纯 Python 足够快（评测 1750 条 <1s）；
- 无原生编译依赖：Windows 开发机无需 MSVC，CI 与本地行为一致；
- 行为可单测（重叠、后缀、failure link），比黑盒依赖更可信。

### 5. 词典是数据文件（与 ADR-1 一致）

- `data/families/*.json`：family / severity / law_refs / penalty / terms（含显式变体、谐音）/
  synonym_phrases；
- `data/normalization/char_map.json`：异体字映射、拆字组件序列；
- 新规 = 新增/修改 JSON，匹配代码不动；词典版本进入匹配器版本号，证据可审计。

### 6. 只承诺"已知变体族"，未知改写单列指标

- PRD R-2 已定义边界：变异攻击面无限，只承诺已知族；
- 评测集拆成三套：**已知变体集**（门禁 ≥95%）、**未知集**（语义改写/未见谐音，如实报低命中）、
  **负样本集**（误报基线）。不把未知集混进门禁，避免自欺。

### 7. 条款解析：锚点切分 + 显式正则，不做"智能理解"

- 切分只认 `第X条`（段首）/`（X）`/`第X章` 锚点；`违反本法第九条规定` 这类行内引用必须
  不切分（有专门检查点守着）；
- 抽取只做可验证的事：引号内禁用词、`X 元以上 Y 元以下` 罚则、`自 YYYY 年 M 月 D 日起施行`、
  指南的 `五、`/`六、` 豁免条目；
- 无法映射的内容保留为 clause，不编造 rule；
- 解析结果经 `POST /admin/regulations/import` 导入 Java 控制面（schema 仍由 Flyway 单一所有者管理）。

### 8. 规则绑定"最细可用条款"

- 条文级（article）与项级（item）都入 `regulation_clause`（item 的 parent 指向 article）；
- rule.clause_id 指向最细条款（如 `ADV-LAW-ART9-ITEM3`），M3 检索可以按条款粒度召回，
  判定证据可以精确到"第九条第（三）项"。

### 9. 导入幂等

- 法规内容 checksum（条款规范化 JSON 的 sha256）比较：相同则跳过重写条款；
- 规则按 `(tenant_id, rule_id)` 去重：已存在则跳过（规则版本由后续编辑流程管理）。

## 后果

**正面**
- 归一化可测（1000+ 变体集、分族指标、误报基线），不是"感觉变强了"；
- 命中可定位到原文 span；
- 新规通过"解析 → 导入 → 激活"三步进库，零代码变更。

**负面 / 已知限制**
- 词典匹配不看语境：`第1期`（词典把"第1"当"第一"的变体）这类序数用法会产生误报，
  需要 M3 条款检索 + M4 模型结合上下文消除；
- 逐字繁简转换保证 offset，但对"乾/干"这类多对一/一多映射可能不如短语级准确；
- 条款解析器针对 2 份文档/11 条条文验证，格式化异常的地方性法规可能解析失败（M3 扩充文档集）；
- 金标由 AI 依据官方文本转录（可复核但非第三方人工），M3 安排外部抽检。

## 被否方案

| 方案 | 否掉原因 |
|---|---|
| Go 侧做归一化 | CJK/拼音/繁简生态薄弱，重复造轮子 |
| 拼音还原成汉字 | 多对一、不可逆，破坏 offset |
| 引入 pyahocorasick 等原生扩展 | Windows 编译/分发成本，CI 行为不一致 |
| 让 LLM 直接做条款结构化 | 结果不可复现、无法逐字段验收；M4 才会用模型做语义判断 |
| 规则写进 Java 代码 | 违反 ADR-1，新规要发版 |
